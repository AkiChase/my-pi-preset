# Monitor：持续监听与通知

Monitor 用来观察持续产生事件的命令或 WebSocket，把输出分批显示在会话里，并唤醒模型处理。只需要“命令结束后告诉我结果”时，用后台 Bash 更合适；Monitor 适合日志追踪、文件变化和持续事件流。

## 发起监听

可以告诉模型：“用 monitor 监听这个日志，只看包含 READY 的行；一分钟没新事件时提醒我，十分钟后停止。”模型调用的 `monitor` 工具参数如下；没有 `/monitor` 斜杠命令。

| 参数 | 用途 |
| --- | --- |
| `command` | 要执行的 shell 命令，与 `ws` 二选一 |
| `ws` | WebSocket 来源：`url` 必填，可带 `protocols` 数组 |
| `description` | 必填的具体说明，每条通知都显示 |
| `wake_absent_ms` | 可选的静默提醒阈值，单位毫秒，必须是有限正数 |
| `timeout_ms` | 可选的总截止时间，单位毫秒，必须是有限正数 |

下面是工具参数示例，不是在输入框里直接执行的命令：

```json
{
  "command": "tail -f ./service.log | grep --line-buffered READY",
  "description": "服务就绪日志",
  "wake_absent_ms": 60000,
  "timeout_ms": 600000
}
```

WebSocket 示例：

```json
{
  "ws": { "url": "wss://example.com/events" },
  "description": "服务事件流",
  "timeout_ms": 600000
}
```

WebSocket 需要运行环境提供相应支持（Node 22 及以上）。二进制消息只记录类型／长度提示，不把二进制内容解码成正文。

启动后返回任务 ID 和日志路径。用 `/tasks` 查看，或让模型通过 `jobs output` 读日志、`jobs kill` 停止监听。取消某次 `jobs attach` 等待不会停止 Monitor。公共快捷键见 [任务管理](task-composition.md)。

## 什么时候通知

同一会话里的所有 Monitor 共用普通进度通知节奏，默认 30 秒。首批输出、静默提醒、恢复和收尾通常在最多 200 毫秒的短窗口中合并；把普通间隔配置得更短时，短窗口也相应缩短。

持续有输出不会不断推迟已经安排的通知，没有新事件也不会定时发空消息。及时通知会一并带走其他待发来源的活动，然后重新计算普通间隔。因此多个监听可能出现在同一批通知中，而不是各发一条。

通知会显示在终端，也会交给模型。模型忙碌时在当前整批工具执行完成后的安全边界接收，不会取消正在运行的工具；不保证每条通知都有单独一条模型回复。

`wake_absent_ms` 从启动或最近一次事件到达算起。每段静默只提醒一次，监听继续；新事件恢复后会及时通知，再开始下一段静默计时。别的监听发通知不会重置这个来源的静默计时。静默不代表成功或完成。

## 命令输出怎么收

命令的 stdout 和 stderr 都会进入同一日志和通知。完整的一行算活动，尚未换行的片段只在收尾时并入，不会单独唤醒模型。stderr 有文字不等于命令失败，最终状态看主 shell 的退出码或信号。

管道仍按 shell 原来的规则运行：

```sh
command | grep --line-buffered pattern       # 只过滤 stdout，stderr 仍会被 Monitor 收到
command 2>&1 | grep --line-buffered pattern  # 两个流都经过过滤
```

管道中的程序需要及时刷新输出，如 `grep --line-buffered` 或 awk 的 `fflush()`。分别重定向 stdout、stderr 仍有效。两个流之间不保证严格时间顺序，通知行序也不保证与合并日志的字节顺序完全一致。

WebSocket 按消息到达计活动：空消息也算，多行消息仍只算一次到达。

## 结束与日志

不传 `timeout_ms` 就没有默认截止时间；需要一直监听到会话结束的任务应自行明确停止时机。

自然结束、失败、外部信号、到达总截止或日志超量时，原因与待发输出会合为收尾通知。显式 `jobs kill`、面板中的 `x` 和会话退出不额外发送收尾批次，已显示的通知也不会撤回。结果已由查询工具报告时不会再重复发完成通知。

命令监听随主 shell 退出结束，不等待它的孙进程继续写输出。通知可能提示后续输出未记录；日志只包含观察范围内收到的内容，不保证保存命令退出后的所有子进程输出。

通知只是有限预览，省略会标出整行、字符和截短行数量。高频输出不会仅因为通知放不下而停止监听，省略的预览也不会删掉观察范围内的原日志。

来源太多、整批通知放不下时，会显示省略来源数量和 `monitor-batch-<uuid>.jsonl` 清单路径。清单保存来源 ID、状态、说明与日志路径；完整输出仍在各自日志中。可以让模型读取清单，找到对应的日志。清单保存失败会明确提示不可用，此时用 `jobs list` 和日志查询，不要把省略的结果当成已经收到；通知提交失败不会自动安排重试。

日志和批次清单不会随着停止或记录回收自动删除，需要自行清理。默认 `/tmp/pi-bg` 可能被系统清理，长期保留请配置其他目录。

## 配置

Monitor 使用 `~/.pi/agent/process-tasks.json`；目录随 `PI_CODING_AGENT_DIR`。有效环境变量优先于文件，文件优先于默认值，例如 `PROCESS_TASKS_MONITOR_FLUSH_MS`。手改文件后在 Pi 中 `/reload`，`/process-tasks-config` 可查看覆盖项和警告。

| 键 | 默认值 | 用途 |
| --- | --- | --- |
| `monitorFlushMs` | `30000` | 普通进度间隔（毫秒）；`0` 按来源回调批次直接发送，首批／及时事件最多等 `min(200ms, monitorFlushMs)` |
| `monitorMaxLinesPerEvent` | `50` | 每个来源的待发正文及输出预览行数上限，不是整批通知的总行数上限 |
| `outputPreviewChars` | `12000` | 同一通知所有来源共享的输出预览预算 |
| `maxLogBytes` | `104857600` | 与其他进程共用的日志大小保护，超量时停止；周期检查间可能短暂超过阈值 |
| `logDir` | `"/tmp/pi-bg"` | 日志和批次清单的目录 |

更多进程配置见 [任务管理](task-composition.md#进程)。
