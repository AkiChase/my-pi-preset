# Monitor session-level notification batching

## 背景

多 monitor 空跑验证中，单个 monitor 已按默认 30 秒窗口合并活动，但不同 monitor 各自维护通知时钟，导致同一主会话反复、交错唤醒。Agent 的组完成通知依赖有限任务的终态，不能直接套用到持续监听源。

## 目标

降低同一主会话多 monitor 的重复唤醒，保持事件来源明确、日志完整，以及结束、静默、恢复等事件的及时性。

## 范围

- 同一主会话内多个 monitor 的活动通知合并。
- 命令型与 WebSocket 型 monitor 均覆盖。
- 保留每个来源的事件缓冲、静默判断及生命周期。
- 普通 bash 后台任务与 agent 的通知行为保持不变。
- 如有公共代码抽取，以必要的投递基础设施为限，不强行统一两种后端的 batching 策略。

## 需求与约束

- 通知按来源区分内容，不重复发送旧事件；没有新事件的来源不生成重复汇报。
- 普通活动使用统一刷新节奏；持续有事件不能无限推迟发送，无待发事件不产生空唤醒。
- 首批及及时事件允许最多 200ms 合并等待；普通节流为 0 时保留不延迟语义。
- 及时事件提前刷新带走其他来源有资格发送的待发活动，并从成功提交重新计算普通间隔。
- 自然完成保留未发输出与终态，不能被普通活动周期长时间拖延。
- 静默提醒与恢复保留及时性；失败与超时不能被普通进度周期拖延。
- 静默依据事件到达时间，不依据共享通知的发送时间；其他来源的通知不能重置本来源的静默判断。
- 人为停止与 shutdown 保持现有静默取消语义，清理待发内容。
- 面板和日志持续更新，合并仅影响外发通知。
- 保留有界预览与完整日志可追溯性；正文和 details 合并后的总通知必须有明确硬容量边界。溢出来源 metadata 可转入完整批次清单，通知保留省略数量及清单路径，不拆批增加唤醒。
- 会话之间不得合并或串发；关闭与重入不能泄漏定时器或发送陈旧通知。

## 验收标准

- [x] 同会话近同时启动的两个 monitor，首批活动在约定窗口内合成一次通知。
- [x] 多 monitor 持续活动共享刷新节奏，一个刷新窗口至多产生一次普通活动通知。
- [x] 单 monitor 的延迟、预览、日志与事件定义满足明确的兼容约定。
- [x] 普通活动、自然完成、静默、恢复、失败与超时的竞争不造成遗漏或重复通知。
- [x] 自然完成通知包含本来源未发输出；其他来源保持正确活动与静默状态。
- [x] 人为停止、shutdown、会话切换及发送回调重入不投递陈旧事件。
- [x] 合并预览达到容量边界时有明确省略信息，并保留各来源日志路径（内联或完整批次清单）。
- [x] 普通 bash 后台任务及 agent 组完成、partial、结果消费抑制不发生行为变化。
- [x] 自动化测试覆盖多源调度、无活动、及时事件抢先刷新、终态竞争、容量边界和会话隔离。

## 实施确认

用户已于本会话批准开始实施，并确认：
- 小于 200ms 的普通间隔采用 min(200ms, monitorFlushMs)，F=0 不延迟。
- 整批共享输出预览预算，按来源公平分配；ID、状态和日志路径单独保留，完整详情在 task 面板／日志查询。
- 提交失败沿用既有消费语义：记录 notifyError、不杀源、进度不自动重放、终态不标已告知，不新增自动重试。
- 不迁移 agent 通知，只抽取 monitor 所需投递基础设施。
- 在当前 main 工作区实施，保留现有 4 个无关 `.pi` 改动，不纳入本任务。
