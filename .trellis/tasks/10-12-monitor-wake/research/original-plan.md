# monitor 提醒任务：需求与验收

状态：需求已确认，待实施。本文件在 `local/`，不进 git。

本文件只负责 monitor 的通知、唤醒及无进度提醒。`local/bg-tasks-plan.md` 是另一个 Agent 正在负责的交互重写任务，不向其中合并本方案，也不改它的界面与生命周期约定。

## 1. 目标

**一条对话通知对应一次可触发 Agent 处理的事件。**

不再每 2 秒往对话里追加不会唤醒 Agent 的消息。间隔内攒输出，到通知时间再一次发出。Agent 空闲时启动处理；正在工作时在安全边界接收，不强制中断正在执行的工具，也不保证每条事件都产生一条独立的 Agent 回复。

不增加新的侧栏、常驻 widget 或滚动预览。全量输出保存在日志中，实时查看沿用现有任务查看入口。

## 2. 配置与参数

### 通知间隔：配置文件控制

默认 **30 秒**，已获用户确认。

复用配置文件 `~/.pi/agent/bg-tasks.json` 的 `monitorFlushMs`，将默认值由 `2000` 改为 `30000`。其语义改为两次普通进度通知之间的最小间隔，不再是被动消息的刷新间隔。

```json
{
  "monitorFlushMs": 30000
}
```

已有显式配置按原值生效；默认值调整不覆盖用户文件中的设置。沿用现有环境变量覆盖规则，不另加一组唤醒预算配置。

### 无进度超时：由 Agent 在启动 monitor 时传入

参数名沿用本次讨论的 `wake_absent_ms`，单位为毫秒；这是待实现的工具参数，不应描述成已有能力。

- Agent 根据所监听任务的预期输出频率传入。
- 不传则不启用无进度提醒，没有隐式默认超时。
- 必须为有限正数；无效参数在启动监听源前报错。
- 与现有 `timeout_ms` 不同：`timeout_ms` 是监听的总截止时间；`wake_absent_ms` 只提醒无进度，不停止监听源。

例如 `wake_absent_ms: 60000` 表示连续 60 秒未收到新的流事件时提醒。

## 3. 通知规则

| 情况 | 何时通知 | 对话与 Agent 行为 |
| --- | --- | --- |
| 首次收到输出 | 立即 | 显示一条通知，并触发 Agent 处理 |
| 正常持续输出 | 距上次进度通知满 30 秒（或配置值），且有未发送输出 | 将期间输出合成一条通知，并触发 Agent 处理 |
| 通知间隔内 | 不通知 | 只缓冲、写日志；对话不增长，不发隐藏的被动消息 |
| 没有新输出，且未启用无进度超时 | 不通知 | 不定时发空消息 |
| 连续无进度达到 Agent 传入的超时 | 立即，只提醒一次 | 显示无进度提醒，并触发 Agent 处理；监听继续运行 |
| 无进度提醒之后首次恢复输出 | **立即，不等 30 秒** | 显示恢复进度通知，并触发 Agent 处理；随后重新按配置间隔合并 |
| 监听源结束、失败或被停止 | 立即收尾 | 将尚未发送的输出与结束结果合为一条通知，不先发末批输出再紧跟完成通知 |

所有通知都同时面向用户和 Agent。不另外发只渲染、不触发处理的消息。

### 正常进度的时间规则

- 30 秒从最近一次进度通知发送时开始计算。
- 通知时没有待发输出，不发空消息。
- 已经过了间隔但一直没有新输出：下一批输出到达后立即通知，不额外再等 30 秒。
- 恢复进度通知视同新的首次进度通知；从恢复通知重新计算下一次普通进度通知时间。

### 无进度提醒的时间规则

- “进度”指监听源到达新的完整 stdout 行或 WebSocket 事件，不解析内容，也不根据是否包含 ERROR 判断进度。
- 从启动监听时开始计时；每次收到新的流事件，重新计算无进度超时。使用实际事件到达时间，而不是合并通知的发送时间。
- **同一段静默只提醒一次**：提醒后即使继续静默，也不每隔一个超时重复刷屏。
- 提醒后首次有进度，立即发送恢复通知，并重新启用无进度计时。
- 之后再次达到无进度超时，可再提醒一次；每段静默都遵循“提醒一次 → 恢复立即通知”的规则。
- 若无进度超时到达时还有未发送的进度，将其并入同一条无进度提醒；不要连发一条普通进度和一条无进度提醒。
- 监听源进入终态后，不再触发无进度或恢复提醒。显式停止是否有收尾通知，沿用现有主动停止的通知抑制规则，不因本任务新增重复通知。

## 4. 用户看到的例子

### 持续输出

假设通知间隔为 30 秒，首次输出在第 0 秒，监听源在第 65 秒结束：

```text
0s   首批进度通知 → Agent 处理
30s  合并 0s 之后至今的待发输出 → Agent 处理
60s  合并上次通知之后的待发输出 → Agent 处理
65s  剩余输出 + 结束结果，一条收尾通知 → Agent 处理
```

中间每秒输出仍写日志，但不每秒或每 2 秒出现在对话里。

### 无进度后恢复

假设通知间隔为 30 秒，Agent 传入无进度超时为 10 秒：

```text
0s   首批输出，立即通知
10s  连续 10 秒无进度，提醒一次
20s  仍无进度，不重复提醒
23s  新输出到达，立即通知“恢复进度”，不等到 30 秒
53s  若期间持续输出，合并为下一条普通进度通知
```

若第 23 秒恢复后又停止输出，第 33 秒可以再次发送无进度提醒。不存在同一段静默每 10 秒重复提醒的问题。

## 5. 通知内容与刷屏限制

- 每批只有一条通知，标明 monitor 名称、进度/无进度/恢复/结束状态以及日志路径。
- 进度通知携带本批待发输出，沿用现有单条内容限制；超出部分报未显示数量，并指向完整日志。
- 无进度提醒说明已多久没有事件、监听仍在运行；不把“无输出”直接判定为程序失败。
- 恢复通知携带恢复后的首批输出；不额外再发同一批普通进度通知。
- 定时发送、无进度提醒和结束同时发生时合并处理，结束优先；同一批输出不能重复消费。
- 不设置生命周期唤醒次数上限，不因提醒次数多而偷偷降级为被动消息。

## 6. 不做什么

- 不增加 `wake_on` 或 ERROR/FAILED 等关键词识别。
- 不增加告警等级、分层投递或额外唤醒预算。
- 不新增常驻日志 widget、侧栏输出或阶段性摘要通道。
- 不更改另一任务负责的悬浮窗、快捷键、列表隐藏与注册表回收行为。
- 不在本次实现中顺带修改 stdout/stderr 分流语义。

## 7. 验收

1. 默认配置间隔为 30 秒；配置为其他数值时按配置发送，显式旧值不被覆盖。
2. 连续输出时首批立即发；后续普通通知间隔不少于配置值。间隔内无任何被动对话消息。
3. 没有新输出且未传 `wake_absent_ms` 时，不定时发送空通知。
4. 超时内持续有新事件，即使尚未到合并发送时间，也不误报无进度。
5. 启动后一直无输出，到超时提醒一次；继续静默不重复提醒。
6. 无进度提醒后恢复输出，立即通知，之后从恢复通知重新计算普通进度间隔。
7. 恢复后再次静默，可再提醒一次；验证两轮“无进度 → 恢复”。
8. 无进度到点但还有待发输出时，只发一条包含待发输出的无进度提醒。
9. 结束时剩余输出与结束结果合为一条通知；结束后无定时提醒，临界时刻不重复发送。
10. 每条通知都使用可触发 Agent 处理的投递方式并显示给用户；忙碌时不强制打断工具。
11. 非法无进度超时参数在启动监听源前报错；未传入时该能力关闭。
12. 全量输出仍可从日志读取；单条通知超过内容限制时明确说明省略情况。

## 8. 本 monitor 提醒任务的后续任务

- **stdout/stderr 语义**：当前 stderr 不产生 stdout 流事件；只写 stderr 的源可能触发无进度提醒。后续单独讨论什么算进度、是否合流以及如何展示错误日志。本轮保留现有语义，不自动加合流开关或失败尾部回退。
- 实际使用后再评估默认 30 秒的响应体验；本轮已确认的默认值不再悬置，也不为此新增复杂预算机制。
