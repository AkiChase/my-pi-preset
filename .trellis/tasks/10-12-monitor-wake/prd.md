# Monitor 通知与唤醒

## 目标

让 monitor 的可见通知成为能触发 Agent 处理的事件，同时避免对话刷屏。静默或输出密集本身不应导致监听停止；通过有界缓冲和通知内容限制控制开销。完整保留观察范围内已接收的日志，显式停止的反馈与后台 shell 对齐。

## 背景与需求来源

原始需求和 12 条验收保留在 [research/original-plan.md](research/original-plan.md)，作为历史输入。

设计讨论中，用户进一步确认了显式停止与 shell 对齐、取消隐式截止和持续速率溢出停止、统一日志大小保护、不考虑旧参数兼容，以及 stdout/stderr 默认合并并均算活动。本 PRD 在这些冲突处取代原方案，其余原始需求继续有效。

## 需求

### 通知、静默与恢复

- `monitorFlushMs` 默认值为 30000 毫秒。保留用户显式值以及现有环境变量覆盖优先级。
- 首批输出立即通知。后续普通进度通知的提交间隔不小于配置值；间隔已经过去但没有待发输出时，下一批输出到达立即通知。
- 两批通知之间只缓冲输出、写日志，不提交被动对话消息或空消息。
- 可选参数 `wake_absent_ms` 必须是有限正数，单位毫秒，在启动任何监听源之前验证。不传即关闭静默提醒，没有隐式阈值。
- 进度指在源事件边界收到 stdout 或 stderr 的完整行，或 WebSocket 消息事件。两个命令输出流默认进入同一日志和通知，不标来源；按完整行到达时间计时，不按通知提交时间或内容关键词计时。通知中省略的输出仍算进度，空 WebSocket 消息也算活动。任一流未换行的片段只在最终读取时并入收尾，不单独唤醒。
- stderr 有内容不代表失败；命令自然结束主要看退出码／信号。工具合并输出不改变 shell 管道：`command | grep ...` 只过滤 stdout，stderr 仍被工具收到；`command 2>&1 | grep ...` 才过滤两流。不承诺合并接收顺序等于事件实际发生顺序。
- 从启动监听开始计算静默时长，每次进度到达重置。每段静默最多提醒一次，提醒后监听继续运行。
- 静默提醒后的首次事件立即产生恢复通知，并重新开始普通通知间隔。之后再次静默可以再提醒。
- 待发输出并入静默或收尾通知，不先后连发重复通知。进入终态后取消进度、静默和恢复定时器；已知终态优先，同一批输出不得消费两次。
- 所有提交的通知都对用户可见，并采用能触发 Agent 处理的投递方式。Agent 忙碌时在安全边界接收，不取消正在执行的工具，也不保证每条通知对应一条独立回复。
- 每条通知包含 monitor 标识、描述、状态和日志路径。静默提醒说明已多久没有事件、监听仍在运行，不把静默判定为失败。

### 生命周期与停止反馈

- 不传 `timeout_ms` 就没有总截止时间，直到源结束、显式停止、资源保护触发或会话退出。删除 `persistent`，不保留兼容别名。
- 显式 `timeout_ms` 是总截止时间：到时停止源，并将停止原因和待发输出合成一条收尾通知，遵守共享通知抑制规则。它与 `wake_absent_ms` 相互独立。
- 删除持续输出速率溢出导致的停止；输出密集的源继续运行。
- 通过 `jobs kill` 或任务面板显式停止时，不新增尾批进度或收尾通知。剩余输出留在日志，停止操作本身反馈结果；不撤回停止前已经提交的通知。
- 自然结束、失败、外部信号终止仍将待发输出和结果合成一条收尾通知，遵守结果已告知及 attach 等共享抑制规则。
- 命令 monitor 随主 shell 的 `exit` 结束，不等待 stdout/stderr EOF 或孙进程关闭管道，也不增加排空时限。进入收尾后同步取走 Node 已缓冲的两个流，只合入同一日志与收尾；随后关闭观察管道。不保证尚未读到或孙进程之后写出的内容，任一流未结束时收尾说明输出可能被截断，不编造未读取数量。
- 不改变会话归属、退出清理、注册表保留及 shell 生命周期行为。

### 有界输出与资源保护

- 待发通知缓冲和单条通知都受行数、字符数上限约束。接收输出时就限制缓冲，不等到生成通知时才截断。
- 已接收输出不因通知内容限制而从日志丢失，明确报告通知省略情况；命令主 shell 退出时的观察截止边界遵循上面的规则。不新增独立的高频输出告警流。
- 普通通知合并和有界内容取代 monitor 专用速率窗口、连续溢出计数；删除这些旧机制。
- 所有 monitor 与后台 shell 一样遵守共享 `maxLogBytes`，没有豁免。共享检查发现超过阈值时停止源，将资源限制原因和待发输出合成一条收尾通知，遵守结果已告知及 attach 抑制。这是磁盘资源保护，不是输出速率限制；周期检查不保证日志大小永不超过阈值。不改变 shell 行为，不新增日志轮转或保留机制。
- 删除旧的 monitor 默认截止、截止上限和速率窗口／溢出配置。不做兼容别名、迁移模式或专门的弃用警告，也不改写用户配置文件；现有的普通未知键处理可以保留。

## 范围

本次包括：可唤醒投递、源到达时间计时、stdout/stderr 默认合并并均算活动、合并通知、可选静默／恢复、收尾输出合并、显式停止对齐、取消隐式截止和速率溢出停止、有界缓冲／通知、统一日志大小保护，以及直接删除旧参数和配置。

本次不做：另一任务的后台交互重写、widget、快捷键、任务列表显示、注册表回收、shell 执行语义修改、输出来源标签、关键词识别、告警等级、唤醒预算、周期性“是否继续监听”提示、新的日志轮转或保留策略。不修改另一 Agent 负责的 `local/bg-tasks-plan.md`。

## 与后续任务的顺序

用户要求先完成本任务，再开始 `10-12-subagents-task-ux`。当前保留 bg-tasks 的目录、Job 生命周期、共享停止和会话归属，不提前实现后续的 process-tasks/agent-tasks/task-ui 命名及面板重构。后续以本任务交付后的 monitor 行为为基线；当前不能让通知调度依赖面板，不能改坏共享 stop、计数、结果抑制或会话清理。具体保护和交付检查见 [research/follow-up-boundary.md](research/follow-up-boundary.md)。

## 验收标准

原始验收 1–12 按已确认的新规则调整：

1. 默认通知间隔为 30 秒；有效的显式配置和环境变量覆盖仍生效，不改写用户文件。
2. 首批进度立即发送；后续普通通知满足最小间隔，覆盖安静间隔后重新到达的情况。批次之间没有被动对话消息。
3. 没有新输出且不传 `wake_absent_ms` 时，不周期性发送空通知。
4. 静默阈值内持续收到源事件时不误报，即使输出仍在缓冲或已被省略。
5. 启动后一直没有事件时，到阈值提醒一次；同一段静默不重复提醒。
6. 提醒后首次进度立即通知恢复，从该次提交重新计算普通间隔。
7. 两轮完整的静默／恢复各自允许一次提醒和立即恢复。
8. 静默提醒到点且有待发输出时，只提交一条合并通知，输出只消费一次。
9. 收尾将待发输出和结果合成一条通知，之后没有定时通知；已知终态边界不重复输出。显式停止不提交尾批或收尾通知。
10. 所有通知路径都提交用户可见、能触发 Agent 的消息，不强制取消工具执行。
11. 非法静默参数在启动监听源前报错，不传时关闭提醒。
12. 观察范围内已接收的两个流输出仍可从同一日志读取；通知截断时明确说明已知省略量。主 shell 退出而任一输出流未结束时立即收尾，并说明可能未记录后续输出，不等待 EOF、不编造未知数量。

生命周期与输出保护调整的新增验收：

13. 不传 `timeout_ms` 时，不因旧的默认截止或隐式上限停止。
14. 显式截止到时停止源，并提交一条带原因的收尾通知；静默提醒不停止源。
15. 持续高频输出本身不导致停止，也不产生独立告警流。待发缓冲和通知受行数、字符数约束；省略事件仍重置静默计时。
16. 工具不再暴露 `persistent`；删除默认截止、截止上限和速率窗口／溢出设置。不添加兼容别名、迁移模式或专门的弃用警告，不改写用户配置文件。
17. 所有 monitor 都受共享日志大小保护。检查发现超过配置阈值后停止，并提交一条说明资源限制的合并通知，不另发尾批或超量警告。保留显式停止及 attach 抑制，不改变后台 shell 行为。
18. 保留后续共享 Task Panel 可用的执行边界：monitor 的 absent/resumed 通知不修改 Job 运行状态或消费结果抑制；现有共享显式停止入口仍无新消息并清理资源，panel 查看／关闭不影响 monitor 调度。共享 shell、快捷键、input、注册表保留和单入口加载行为不变；本任务交付后，后续再改名及接入 shared task-ui。
19. 命令 monitor 默认接收 stdout 和 stderr 到同一日志／通知，任一流完整行都重置静默计时；仅 stderr 输出且退出 0 时仍 completed。两流 UTF-8／部分行不错误拼接，缓冲有界；无来源或严重度标签，不断言跨流固定顺序。`command | grep`、`command 2>&1 | grep` 和显式分别重定向仍遵循 shell 语义；仅 stderr 导致日志超限也触发共享保护。
